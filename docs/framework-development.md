# 框架开发与封装规范

## 适用对象与规则级别

本文供编写、封装和维护 AndroidMVIBase 本身的人与 AI 使用，包括公共模块、构建配置、示例宿主及其文档的维护。

在业务项目中接入框架的使用者阅读模块 README 和 [使用者 Skill](../skills/android-mvi-base/SKILL.md)。接入方的业务包名、开发节奏和提交规则由业务仓库决定，不继承本仓库的教学流程。

- **必须**：当前开发规范，新增和修改相关代码时遵循。
- **建议**：优先选择，允许根据具体场景采用其他方案并说明理由。
- **待设计**：尚未确定，不作为现有代码的 Review 违规依据。

本规范确立目标约束，不表示历史实现已全部符合。发现旧代码不符合时列明差异，仅在当前授权范围内修复；不得顺带全仓重构。用户当前明确要求优先。

## 1. 模块与依赖

### MOD-01：公共能力与示例业务分离（必须）

- 新模块与 `app` 同级，不再添加 `core/` 容器层；创建前说明职责、调用方和依赖方向。
- `app` 是示例宿主；`common` 放跨能力使用的公共类型；`network` 放通用网络能力。业务 API、业务 DTO 和演示 Repository 不因网络相关就进入公共 network。
- 公共模块不能依赖 app，模块之间不能形成依赖环。新包或模块应有实际代码用途，不预建空目录。
- 每个正式模块同步创建 README，登记到根 README；使用同一模块模板要求，见 DOC-02。

**原因与检查**：业务换成另一个领域时，公共模块不应被迫删除演示业务或反向依赖宿主。Review 检查实际 Gradle 依赖和公开类型引用。

### MOD-02：依赖暴露与配置归属（必须）

- 依赖版本维护在版本目录。添加或升级依赖时核实当前官方文档、维护状态和兼容范围，不凭记忆拼接版本号。
- 默认使用 `implementation` 隔离内部依赖；公开 API 暴露第三方类型时，明确选择 `api` 导出还是要求消费者直接声明依赖，并在 README 写清楚。
- Gradle 运行 JDK、Java/Kotlin 字节码目标分别说明。沿用 AGP 内置 Kotlin 方向，升级插件时验证兼容性，不以关闭检查代替根因处理。
- 正式封装需要明确宿主配置入口：服务地址、认证来源和业务错误映射不能固定为演示业务；演示默认值明确标记。

## 2. 包、类型和文件命名

### NAME-01：包结构（必须）

- 公共模块命名空间和包名前缀使用 `com.ttxz.base.<module>`，包段全小写，源码路径对应 package 声明。
- 按具体能力或职责组织包；现有例子是 `common.result`、`network.di`。不要把不同职责都放入 `utils`、`manager` 或 `base`。
- 示例业务使用独立功能包，具体路径在示例阶段确定；使用者自己的业务工程不要求改成 `com.ttxz.base`。

**检查**：仅看包名与类名能否判断所属能力？移动类时是否更新引用、文档和示例？

### NAME-02：类型与成员命名（必须）

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 类、接口、object、类型别名 | UpperCamelCase，表达职责 | `AppResult`、`NetworkModule` |
| 普通函数与属性 | lowerCamelCase；函数表达动作，属性表达数据 | `safeApiCall`、`message` |
| 返回 Unit 的 Compose UI 函数 | UpperCamelCase，表达 UI 角色 | `Greeting` |
| 布尔值 | 按语义使用 is / has / can 等形式 | `isLoading`、`hasNextPage` |
| 常量 | UPPER_SNAKE_CASE | `DEFAULT_TIMEOUT_SECONDS` |
| Android 资源 | 小写加下划线，名称表达用途 | `ic_launcher_foreground` |

- `Base` 仅用于承担继承契约的基类；不因仓库是基础框架就给所有类加 Base。
- `Impl` 用于区分确有必要的接口和实现，不要求每个类都成对生成接口。
- 同一概念保持同名；不得同时引入职责相同的 Result、Resource、Response 包装而不说明语义区别。

### NAME-03：文件组织（建议）

文件通常以主要类型命名。紧密相关的小类型和扩展函数可以放在同一文件，如 AppResult 及其回调扩展。独立职责拆文件，不以固定行数或“一文件只能一类型”机械拆分。

## 3. 封装设计

### DESIGN-01：先展示调用方式（必须）

新增公共封装前，在当前任务中说明：具体问题、最小调用示例、框架与宿主各自职责、失败/取消行为、为什么需要新增抽象。内容可直接在对话中给出，小改动不要求单独设计文档。

涉及新公共接口、模块边界或有多种明显取舍的设计时，先完成本学习步骤的设计对齐，再实现。

**检查**：调用方是否必须知道内部实现才能使用？删除某层抽象后是否仍能清楚表达同一能力？不得为尚无场景的扩展预建多层接口、万能基类或复杂配置系统。

### DESIGN-02：统一机制，保留业务决策（必须）

- 网络执行、结果类型等机制可统一；业务响应码含义、会话失效后的导航等决策明确由谁提供。
- 不把网络、Toast、导航、认证和页面状态全部绑定进一个通用基类。
- 优先复用或改进现有能力。维护者可以修改 AppResult 等公共 API，但要评估调用方影响，不能把“业务必须复用”解释成“框架永远不能演进”。

**建议**：能用小函数、组合或具体类清楚表达时，先不用继承体系；需要生命周期共享或真正多实现时再引入对应抽象。

## 4. 公共 API 与 Kotlin 写法

### API-01：控制公开范围（必须）

实现细节使用 private / internal；public API 是有意给消费者使用的契约。避免无意义的 open、可变全局状态和隐藏依赖。优先 val、不可变结果与显式依赖传入；object 用于无状态能力或有明确生命周期的对象。

空值必须有明确含义；不以 `!!` 掩盖未知状态。配置非法、业务失败、暂时无数据分别表达，避免全部返回 null、空列表或“Unknown error”使调用者无法区分。

### API-02：描述行为与演进影响（必须）

公开函数明确输入、返回值、可预期失败，以及涉及的线程、取消、生命周期或资源归属。只有与该 API 有关的项需要说明。

修改签名、默认值、错误语义或可见性时，搜索所有调用者，同步示例与文档；影响已有接入方式时说明迁移方法。当前仓库未发布，也不能以此忽略调用链检查。

## 5. 协程、状态与错误

### ASYNC-01：保持取消和生命周期语义（必须）

- CancellationException 继续传播，不当成普通请求失败；广泛捕获 Exception 时显式处理取消。
- 协程作用域、Dispatcher 和任务寿命应有明确归属。挂起函数不意味着其中任意阻塞操作都自动安全；阻塞工作安排在合适的执行环境。
- 不使用无归属的后台任务来规避生命周期；需要跨页面或持久任务时单独设计其管理方式。
- 暴露只读状态；并发更新、重复请求、取消和过期结果的处理按实际场景验证。

### ERROR-01：结果语义不混淆（必须）

- 区分 HTTP 失败、IO/解析失败、服务端业务失败和取消；保留必要诊断信息，不把底层异常直接作为稳定的用户文案契约。
- 声明是否检查 Response<T> 的 HTTP 成功状态、是否解析业务码；不得将“未抛异常”一概描述成“业务成功”。
- AppResult.Loading 只是值，不自动产生加载过程；请求结果与整个页面 UiState 分开设计。
- 日志、重试和超时要有可说明的范围；面向正式业务的默认日志避免输出敏感正文、凭据，示例服务配置明确标记。

**现有差异**：NetworkCall 当前捕获 Exception，网络日志当前固定 BODY。它们仍是待修正项，本规范不会自动修改这些实现。

## 6. 注释、模块文档与学习

### DOC-01：KDoc 描述契约（必须）

公共类型和函数添加 KDoc；公开字段、参数含义不明显时补充说明。默认中文解释，标识符用英文。简单内部代码不要求逐行注释，也不强制维护作者、创建日期等 Git 已记录的信息。

写法示例（说明格式，不是对当前 API 已完成行为的声明）：

```kotlin
/**
 * 用一句话说明能力与使用场景。
 *
 * 说明与本 API 有关的线程、取消、失败或资源行为。
 * @param block 调用者提供什么，以及需要遵守什么约束。
 * @return 返回值的语义与限制。
 */
```

注释与当前实现一致。`safeApiCall` 应说明不产生 Loading、不主动切线程，以及实际错误处理范围，不能只写“统一请求”。复杂逻辑注释解释原因和边界，不翻译每行代码。

### DOC-02：README 是可用的接入说明（必须）

每个模块包含：职责/边界、当前能力、关键文件、依赖与接入步骤、最小示例、学习顺序与练习、验证方法、已知限制与待完成项。

长教程放 README，调用契约放 KDoc。示例区分真实源码和拟议写法；依赖已加入不等于功能已封装。API 或可观察行为变化时同步更新 README、使用者 Skill 的相关约束及引用。

### LEARN-01：逐步建设（必须）

每步先提醒“这一步需要你学习”，解释目标、真实文件、必要概念与验收标准；完成当前步骤后给小练习，等反馈再进下一学习阶段。用户明确要求连续完成某范围时按范围推进；日常接入方不受此教学节奏约束。

## 7. 验证与 Review

### VERIFY-01：证据匹配行为（必须）

公共行为变化验证成功路径及受影响的失败、取消、边界条件。构建验证编译与集成，单测验证行为，设备/服务测试验证相应运行场景；报告分别列明结果，不互相替代。

纯文档改动核对源码一致性、链接和规则可用性，不重复 Android 构建。不编写只检查实现字样或模板结构的低价值测试。

### REVIEW-01：同时检查调用方体验（必须）

Review 覆盖：职责/依赖、命名、公开范围、最小调用方式、错误/取消契约、默认配置、兼容影响、注释文档、验证证据。仅针对实际存在的实现评价，不要求为待设计项补齐整套功能。

先列问题，再列不确定项和覆盖范围。问题包含文件/行号、触发条件、影响、建议，可引用规则编号；“建议”项不能仅因风格不同而标成缺陷。Review 本身不授权修复。

## 8. 规则维护与待设计事项

一条规则采用“编号 + 标题 + 级别”，正文写适用条件、具体约束；不直观的规则附原因、检查方式或小示例。通用规则只维护在本文；维护者 Skill 负责执行流程，使用者 Skill 只描述接入契约。

当前待设计：MVI 基类 API、State/Event/Action/Effect 名称与交付语义、页面/示例功能包结构、网络配置入口、统一业务错误策略、发布与版本兼容策略。对应步骤设计落地后同步调整本文和模块说明，不提前当成现行硬规则。

新增自动格式化、静态检查或依赖插件需单独明确范围；本文件不隐含安装工具、自动提交或推送授权。
